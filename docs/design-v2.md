## Problem Statement

174명 규모 한국 회사에서, 사업전략실(CEO 직속, 5명) 소속 founder가 추진하는 사내 도구. 현재 5명이 종이로 자발적으로 작성 중인 데일리 brain dump + 시간블록 워크플로우를 디지털화하여 174명 전 직원에게 top-down 배포. 진짜 customer는 매니저(팀장/본부장/경영진)이며, 174명 직원은 data source 역할. 매니저가 데이터를 활용해 managing, 인력 planning, KPI 평가를 수행. 즉, **세련된 UX(brain dump + 10분 time block)로 modernize된 강제 업무일지**.

## Demand Evidence

- **확인된 evidence (cohort 1)**: 사업전략실 5명이 종이로 오랫동안 자발적으로 사용 중. self-selection bias 있음(strategy office는 회사에서 가장 planner-친화적인 cohort).
- **추측 단계 (cohort 2)**: 사업전략실 외 169명에 대한 demand는 검증되지 않음. founder가 의도적으로 demand validation skip 결정함(vision-driven mode).
- **Honest disclosure**: 이 프로젝트는 demand-driven이 아니라 vision-driven으로 진행됨. founder가 risk를 인지하고 owns 함.

## Status Quo

**미확인**. 사업전략실 외 169명이 현재 daily planning을 어떻게 하는지(Notion / 종이 / 메모장 / 안 함) 조사 안 됨. **Pre-launch에 최소 3명, 권장 10명 인터뷰**(영업/개발/회계/행정 등 다양한 직무 대표). The Assignment에 최소 3명 명시, 가능하면 10명까지 확대.

## Target User & Narrowest Wedge

- **Customer (value buyer)**: 팀장 / 본부장 / 경영진. 매니저 dashboard 가치를 사는 주체.
- **User (data source)**: 174명 사내 임직원. 강제 사용. 매니저가 본다는 사실 명시.
- **Narrowest wedge**: 사업전략실 5명 + 1개 본부 pilot (~30-40명, 본부장 1명) → 6주 운영 → 데이터 보고 전사 확대 결정. 처음부터 174명 일괄 배포는 risk 너무 큼.

## Constraints

- 사내 only, 외부 B2C/B2B SaaS 가능성은 의도적으로 닫음
- Top-down mandate (사용자 자발성에 의존하지 않음)
- KPI / 인사 데이터 통합은 **Phase 2** (MVP는 manual KPI tag)
- 한국 개인정보보호법 + 근로기준법 compliance 필수
- **데이터 residency 한국 내**(P9에서 lock — 외부 SaaS DB 사용 가능 여부가 stack 결정의 first question)
- 매니저 visibility는 핵심 feature(숨기지 않음, 사용자에게 명시)

## Premises (founder 동의 완료, P1-P9, revised)

- **P1**: Brain dump UX(왼쪽) + 10분 time block(오른쪽). MVP 시점 view scope: **일+주 × 개인+팀** (4개). 월/분기/반기/연 + 본부/전사 롤업은 Phase 2. 데이터는 처음부터 누적되도록 schema 설계, view만 단계적. Roll-up은 read-time aggregation으로 시작(Postgres SQL), 성능 이슈 시 materialized view.
- **P2**: Customer = 팀장/본부장/경영진.
- **P3**: User = 174명 사내. 강제 사용. 매니저 visibility 명시.
- **P4**: Vision-driven, demand validation skip. **MVP는 manual KPI tag, Phase 2에서 HRIS 연동으로 자동 누적**.
- **P5**: 사내 only.
- **P6**: 사내 web app(PWA, 모바일 반응형) + SSO. 모바일 native 앱 안 만듦(향후에도 PWA만). 모바일 레이아웃: brain dump와 time block을 tab 전환(작은 화면 stack 안 함).
- **P7**: CEO pitch는 "회사 운영 효율화 + 매니저 의사결정 지원"이 official goal. "개인 성장"은 promise하지 않음(실현되면 보너스).
- **P8**: 6주 metric은 사용률(강제이므로 무의미) 대신 (a) 매니저 의사결정 활용 횟수, (b) entry의 substantive ratio(theater 비중), (c) 6개월 후 retention/퇴사 intent, (d) 매니저 만족도. CEO와 사전 합의 필수. 측정 protocol: 주간 random 50개 entry sample → 2명 reviewer 5점 척도 → AI second opinion → 평균.
- **P9**: Legal pre-check 필수 — 개인정보보호법(보관/파기/열람권), 근로기준법(업무 데이터 KPI 활용 명시), 노조/직원협의회(있다면) 사전 sound out. **첫 질문: "외부 SaaS DB(Supabase 등) 사용 가능 여부"** — 이 답이 stack(Supabase vs 사내 Postgres) 결정.

## Data Model (MVP stub)

핵심 entity 6개:

- `users`: id, email, name, team_id, division_id, role, hire_date
- `teams`: id, name, division_id, lead_user_id
- `divisions`: id, name, head_user_id
- `entries`: id, user_id, date, brain_dump_text, created_at, updated_at, kpi_tags[]
- `time_blocks`: id, entry_id, start_minute, end_minute(10분 단위), description, status(planned/done/skipped)
- `digests` (Phase 1.5): id, scope(team/division), period(daily/weekly), content, generated_at

운영 시간: 09:00-21:00(54 슬롯/일). 입력 cutoff: 익일 11:00까지. 사후 수정: cutoff 전까지 본인만, 이후 audit log 남김.

## Authorization Matrix (MVP)

| Role | own_entry | team_entries | division_entries | all_entries |
|---|---|---|---|---|
| Employee | RW | (own only) | - | - |
| Team Lead | RW | R(team) | - | - |
| Division Head | RW | R(division) | R(division) | - |
| Exec / CEO | RW | - | - | R(all) |
| HR | - | - | - | R(aggregated only) |

수정/삭제는 본인 only(cutoff 전). 매니저는 read-only. 모든 read는 audit log.

## Data Retention (default — 법무 조정)

- Active entries: 작성 후 3년 보관
- 퇴직자: 퇴직 후 30일 내 anonymize(이름→UUID 치환), 데이터는 통계용으로 5년 추가 보관
- 본인 열람권: 언제든 자기 entry 전체 export 가능
- 본인 삭제권: 개인정보보호법상 요청 시 30일 내 처리

## Approaches Considered

### Approach A: 최소 실행 (Web form) — **선택됨**

- 간단한 web form: brain dump textarea + 10분 슬롯 그리드(54개)
- 자동 저장: P9 답에 따라 Supabase(외부 DB 가능) 또는 사내 Postgres(불가)
- 매니저 dashboard: 팀별 entry 목록 view(MVP). 메일 디지스트는 v1.1로 defer.
- AI 사용처: substantive ratio 판정에만(주간 batch). 데이터 외부 송신은 P9 답에 따라 결정 — 불가 시 internal LLM 또는 사람 sampling.
- 모바일: PWA, brain dump와 time block을 tab 전환.
- 기술: Next.js (PWA) + Postgres (Supabase 또는 사내) + 사내 SSO
- Effort: 인간 ~4-6주(SSO/legal lead time 포함) / Claude Code: 코드 작성만 ~3-5일, integration/review/legal 별도
- Risk: 낮음
- Pros: 빠른 launch, 실패 cost 작음, 진짜 사용 데이터 4-6주 내 확보, iterate 가능
- Cons: differentiation 약해서 매니저가 "Notion + Google Form 수준 아냐?"라고 느낄 수 있음, theater 방어 design 거의 없음

### Approach B & C (요약)

- **B (풀 빌드)**: 자체 앱 + AI + zone 분리. 인간 3-4개월. 처음부터 안 골랐으면 다시 안 옴(현실적 pivot path 아님).
- **C (기존 협업툴 위 bot)**: KakaoWork 등 위에 bot. 인간 4-6주. A로 launch 후 데이터 보고 pivot 가능 path. 실패 시 회수 비용 작음(visible failure 아님).

## Recommended Approach (founder 선택: A)

founder는 A 선택. 이유는 (a) explore-first 전략으로 빠른 launch 후 진짜 데이터 보고 결정, (b) C의 시각적 vision 양보 trade-off를 받아들이기 어려움.

A의 known weaknesses(매니저 underwhelm, theater 방어 약함)를 launch 시점부터 인지하고 mitigation plan 가지고 진행. **권장 진화 경로: A → A+ (UX/AI 보강) 또는 A → C (KakaoWork pivot). B로 회귀는 비현실적.**

## Open Questions

1. **사내 messenger / 협업툴이 무엇인가?** (KakaoWork? Slack? Naver Works? Microsoft Teams?) → C로 pivot 시 critical, A에서도 알림 가능성 결정.
2. **사내 SSO 인프라가 무엇인가?** (Google Workspace? Active Directory? 자체?) → P6 구현 결정. **IT팀 ticket SLA 별도 산정**(한국 회사에서 4주 넘기는 일 흔함).
3. **사업전략실 외 169명이 현재 daily planning을 어떻게 하는가?** → status quo 조사 안 됨. Launch 전 ~10명 인터뷰 권장(최소 3명).
4. **CEO buy-in이 어느 단계인가?** 분기별 action:
   - "이미 합의됨" → P7/P8/P9 confirm 미팅 30분으로 충분
   - "초기 논의 단계" → 30분 미팅 + 1주 후 follow-up + 명시적 sign-off 받기
   - "아직 안 함" → 30분 미팅으로 부족, 사전 자료(현재 5명 종이 사용 evidence + 매니저 가치 case + R1-R4 risk + P8 metric)를 정리해서 1차 미팅 → 2차 결정 미팅
5. **노조 / 직원협의회가 있는가?** 있으면 사전 sound out 일정 추가 필요. **없다고 가정한 W4 launch는 risky** — 있으면 W6-W8로 밀림.
6. **HRIS / KPI 시스템이 무엇인가?** Phase 2 자동 누적 연동 대상. MVP는 manual tag.
7. **사업전략실 5명의 종이 양식 실물이 있는가?** → digital UX 설계 시 직접 참조 가능.

## Success Criteria

P8 기준. **사용률 metric 사용 금지. 강제 compliance도 metric 아님.**

- **A급 (진짜 성공)**: 매니저가 도구로 의사결정한 횟수 >= 주 3-5회/본부장당, entry의 substantive ratio >= 60%, 6개월 후 retention 변화 < 1%p
- **B급 (부분 성공)**: 매니저 만족도 >= 7/10, entry의 substantive ratio >= 40%, 사업전략실 외 1개 본부 자발적 추가 도입 의향
- **C급 (실패하지만 죽지 않음)**: 사업전략실 5명 + 추가 10-20명 안정적 사용. wedge로 다음 iteration 명분 확보

CEO와 launch 전 위 metric 합의 필수.
